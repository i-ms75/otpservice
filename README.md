# OTP Service

A small Spring Boot + Redis microservice that gates sensitive actions (e.g. editing
vault data) behind **multi-owner OTP approval**. A client requests an action;
every configured approver receives their own 6-digit code by email; the client
must collect **all** of those codes and submit them together to be approved.

The codes are never stored in plaintext — they are kept as HMAC-SHA256 digests in
Redis with a 5-minute TTL, and every record self-expires.

---

## How it works

```
Client                       OTP Service                     Gmail / approvers
  │  POST /api/generate          │                                  │
  │  body: "<requestId>"         │                                  │
  │ ───────────────────────────▶│ generate one 6-digit code        │
  │                              │ per approver                     │
  │                              │ email each code ────────────────▶│
  │                              │ store HMACs in Redis (TTL 5m)    │
  │ ◀──────── 201 Created ───────│                                  │
  │                              │                                  │
  │ (client collects all codes from the approvers)                 │
  │                              │                                  │
  │  POST /api/verify            │                                  │
  │  { requestId, otps:[...] }   │                                  │
  │ ───────────────────────────▶│ all codes match? → delete record │
  │ ◀──────────── 200 OK ────────│ (max 3 attempts, then locked)    │
```

The set of approvers is **backend-configured** (the `approvers` property) and is
never supplied by the client. The number of codes the client must submit equals
the number of configured approvers (currently the `/verify` endpoint expects
exactly **3**).

## API

Base URL: `http://localhost:8080`

### `POST /api/generate`

Generates and emails one OTP per approver, then stores the hashed codes under
`OTP:{requestId}` with a 5-minute TTL.

- **Request body:** the raw `requestId` string (a UUID generated by the client),
  sent as plain text — *not* wrapped in JSON.

  ```
  3f2504e0-4f89-41d3-9a0c-0305e82c3301
  ```

- **Responses:**

  | Status            | Meaning                          |
  |-------------------|----------------------------------|
  | `201 Created`     | Codes generated and emails sent  |

### `POST /api/verify`

Submits all the collected codes. If every approver's stored hash is matched by
one of the submitted codes, the record is **deleted** and verification succeeds.

- **Request body:** JSON

  ```json
  {
    "requestId": "3f2504e0-4f89-41d3-9a0c-0305e82c3301",
    "otps": ["123456", "654321", "111222"]
  }
  ```

  `otps` must contain exactly **3** codes.

- **Responses:**

  | Status                  | Meaning                                              |
  |-------------------------|------------------------------------------------------|
  | `200 OK`                | All codes matched — record consumed                  |
  | `400 Bad Request`       | `otps` did not contain exactly 3 codes               |
  | `404 Not Found`         | Unknown or expired `requestId`                        |
  | `406 Not Acceptable`    | Verification failed (response includes attempts left) |
  | `429 Too Many Requests` | Max attempts (3) exceeded — record invalidated        |

> **Note:** a successful verify deletes the record, so verification is **not**
> idempotent — a second `/verify` for the same `requestId` returns `404`.

`GET /actuator/health` — used by the Docker and deployment health checks.

## Getting started

### Prerequisites

- **JDK 17** (only needed for running locally without Docker)
- **Docker** + **Docker Compose** (for the containerized path)
- A **Redis** instance (Docker Compose provides one)
- A **Gmail account with an App Password** — see below

#### Create a Gmail App Password

1. Enable **2-Step Verification** on the Google account.
2. Go to **Google Account → Security → App passwords** and generate a 16-character
   password.
3. Use that App Password (not your normal account password) as the mail password.

### 1. Clone

```bash
git clone https://github.com/<your-org>/otpservice.git
cd otpservice
```

### 2. Configure secrets

Copy the example env file and fill in real values:

```bash
cp .env.example .env
```

`.env` is git-ignored and is read automatically by Docker Compose:

```ini
# --- Redis ---
SPRING_DATA_REDIS_PASSWORD=change-me

# --- Gmail SMTP ---
SPRING_MAIL_HOST=smtp.gmail.com
SPRING_MAIL_PORT=587
SPRING_MAIL_USERNAME=your-email@gmail.com
SPRING_MAIL_PASSWORD=your-gmail-app-password

# --- Application ---
PEPPER=generate-a-strong-base64-secret          # used to HMAC the OTPs
APPROVERS=email1@example.com,email2@example.com,email3@example.com
```

Generate a strong pepper with:

```bash
openssl rand -base64 32
```

### 3. Run with Docker Compose (recommended)

Compose references the image published to GHCR (`ghcr.io/i-ms75/otpservice`), so
this pulls the latest released image, starts Redis (password-protected), and
starts the service:

```bash
docker compose up -d
```

> The image is built in CI (see [Deployment](#deployment)) — Compose no longer
> builds it. To run uncommitted local changes, build and tag the image yourself
> first, then start the stack:
>
> ```bash
> docker build -t ghcr.io/i-ms75/otpservice:latest .
> docker compose up -d
> ```
>
> Or skip Docker for the app entirely and use the
> [local run](#4-run-locally-without-docker) path below.

The API is then available at `http://localhost:8080`. Check health with:

```bash
curl http://localhost:8080/actuator/health
```

### 4. Run locally without Docker

You still need a running Redis. Start one quickly with:

```bash
docker run -p 6379:6379 redis:7
```

Then provide configuration via environment variables (which override
`src/main/resources/application.properties`) and run the app:

```bash
export SPRING_DATA_REDIS_HOST=localhost
export SPRING_DATA_REDIS_PORT=6379
export SPRING_DATA_REDIS_PASSWORD=...     # only if your Redis requires auth
export SPRING_MAIL_USERNAME=your-email@gmail.com
export SPRING_MAIL_PASSWORD=your-gmail-app-password
export PEPPER=$(openssl rand -base64 32)
export APPROVERS=a@example.com,b@example.com,c@example.com

./mvnw spring-boot:run
```

(Use `mvnw.cmd` on Windows.)

### 5. Try it out

```bash
# 1. Generate codes for a request (the approvers receive the emails)
REQ=$(uuidgen)
curl -X POST http://localhost:8080/api/generate \
  -H "Content-Type: text/plain" \
  -d "$REQ"

# 2. Verify with the three codes collected from the approvers
curl -X POST http://localhost:8080/api/verify \
  -H "Content-Type: application/json" \
  -d "{\"requestId\":\"$REQ\",\"otps\":[\"123456\",\"654321\",\"111222\"]}"
```

## Configuration reference

These keys live in [application.properties](src/main/resources/application.properties)
and can each be overridden by an environment variable (Spring relaxed binding,
e.g. `spring.data.redis.host` → `SPRING_DATA_REDIS_HOST`):

| Property                     | Purpose                                   |
|------------------------------|-------------------------------------------|
| `approvers`                  | Comma-separated approver emails           |
| `pepper`                     | Secret key for HMAC-SHA256 hashing of OTPs |
| `spring.mail.host` / `port`  | SMTP server (Gmail)                       |
| `spring.mail.username`       | Sending Gmail address                     |
| `spring.mail.password`       | Gmail **App Password**                     |
| `spring.data.redis.host` / `port` / `password` | Redis connection        |

## Deployment

Pushing a **version tag** (e.g. `1.0.0`) triggers
[.github/workflows/deploy.yml](.github/workflows/deploy.yml), which runs two jobs:

1. **build** — on a native `arm64` runner (matching the Graviton EC2 host), builds
   the image from the multi-stage [Dockerfile](Dockerfile) and pushes it to GHCR as
   `ghcr.io/i-ms75/otpservice:<tag>` and `:latest`. Uses the built-in `GITHUB_TOKEN`,
   so no registry credentials are required.
2. **deploy** — SSHes into the EC2 host, clones the tag for `docker-compose.yml`,
   writes `.env` from GitHub Environment secrets, logs in to GHCR with the job's
   short-lived token, then `docker compose pull && docker compose up -d`. No build
   happens on the box.

Manual runs are also available via `workflow_dispatch`.

> On the **first** deploy, GHCR creates the package as **private** even for a public
> repo; the deploy step's `docker login` still pulls it. Make the package public in
> the repo's Packages settings if you want unauthenticated pulls.

Required secrets (under the `prd` GitHub Environment): `EC2_HOST`, `EC2_USER`,
`EC2_SSH_KEY`, optionally `EC2_SSH_PORT`, plus the runtime secrets
`SPRING_DATA_REDIS_PASSWORD`, `SPRING_MAIL_USERNAME`, `SPRING_MAIL_PASSWORD`,
`PEPPER`, `APPROVERS`.

```bash
git tag 1.0.0
git push origin 1.0.0
```

## Security notes

- OTPs are stored only as HMAC-SHA256 digests (`email|code`) keyed by a server
  pepper; plaintext codes exist only in the emails.
- Comparisons are constant-time (`MessageDigest.isEqual`) and failure responses
  are generic.
- Records and the attempt counter both carry a 5-minute TTL; after 3 failed
  attempts the record is invalidated.
- The endpoints are **unauthenticated by design** — deploy this service behind a
  trusted network/gateway boundary. The calling application is the trust boundary.
- All secrets are injected via environment variables; `application.properties`
  holds only `${...}` placeholders, so no credentials live in the repo. Keep your
  real values in the git-ignored `.env` (or GitHub Environment secrets for deploy).
